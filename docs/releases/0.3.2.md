# shim-cli 0.3.2

A bare number in a tool result is no longer mistaken for a phone number.

## Bare numbers are not phone numbers

The phone recogniser masked almost any bare run of digits, because the
`phonenumbers` library accepts nearly any ten digits in one of nine regions. A 2026 Unix timestamp, a ten-digit id, or the decimals of a float
came back as `<PHONE_n>`. A JSON file read through the hook stopped being JSON:

```
"created": <PHONE_1>
```

and a cost line read `cost 0.<PHONE_1>`.

A bare run of digits — no `+`, space, hyphen, dot, slash or parenthesis — is
now a phone number only in two cases:

- It is Turkish-shaped: a mobile number such as `5321234567`, `05321234567` or
  `905321234567`, or a landline with trunk 0 such as `02125551234`.
- A phone cue sits within 16 characters before it: `tel`, `telefon`, `phone`,
  `gsm`, `cep`, `mobile`, `mobil`, `fax`, `whatsapp`, `call`, `numara`, `num`
  or `no`. Cues are Turkish and English only.

A decimal such as `0.0376118499` is never a phone number. Timestamps, ids and
floats in a tool result now reach the model unchanged, and a JSON file stays
JSON.

Formatted numbers are masked exactly as before: `+90 532 123 45 67`,
`(555) 123-4567`, `0212 555 12 34`, `01.23.45.67.89`.

Not detected: a bare number in another national format with no cue, for example
a CSV column of US numbers whose header is on another line. A
[custom pattern](../commands.md#shim-config) covers that case.

A bare candidate that is rejected is not masked, but it is counted. The session
summary shows it on its own line:

```
warned    12 PHONE (bare numbers, left as they were)  (Read orders.json)
```

and `shim report --json` carries it as `bare_numbers`. The line never appears
at zero. A log-heavy session can show a large number there; it is information,
not a leak.

## Listing text a visitor can read

The Claude and Codex listings, and both plugin manifests, now say what a person
gets instead of the repository's vocabulary: Claude masks secrets and personal
data in tool results, Codex reports what was in a prompt. A test holds each
listing equal to its manifest. `shim help` opens with the README's one-liner,
and the READMEs no longer say the hook archive may be missing: it is committed
on `main` and on every tag.

## Doctor says what is true

`shim doctor`'s coverage table now reads the client's hook file. Before
install it says `0 of 5 events installed; run shim install claude.` with `no`
in every row, where it used to say `5 of 5` whatever was on disk. The version
warning no longer fires on Claude Code 2.1.263, the version this release was
verified on, and "not installed" names the command that installs it. With
Codex absent from `PATH`, the hook-support line says it was not checked rather
than repeating that the executable was not found.

## Installing on a Python 3.9 machine

The package runs on CPython 3.10 through 3.13. On a machine whose only Python
is 3.9, the plugin route needs no Python beyond 3.9 and the package route needs
`--python`: `uv tool install --python 3.12 --compile-bytecode shim`.

## The model is told what was masked

A masked tool result reached the model with placeholders and nothing else. Asked
for a value in a `.env` it had read through the hook, the model saw
`SUPPORT_EMAIL=<EMAIL_1>` and told the user:

> that's a literal placeholder string in the file, not a real email address — the file contains placeholder tokens rather than actual values.

Claude Code's `PostToolUse` output now carries one more field beside the masked
result, `additionalContext`, which reaches the model and not the screen:

```
shim: masked EMAIL (1), SECRET (1) in Read. Placeholders such as <EMAIL_1> stand for real values in the source; the source does not contain placeholders.
```

It names entity types, counts and the tool, never a value. The same question
now gets:

> `<EMAIL_1>` is a placeholder standing in for the real address; it isn't
> what's in the file.

(Claude Code 2.1.263.)

Nothing else changes: the session summary, `shim report`, a compacted result
and a masked tool argument are exactly as they were.

## `shim watch` says what it measured, and on whose bill

Three lines of the watch report were true of a subset and read as true of the
whole. With a subscription sign-in and four parallel requests, two of which
arrived while both inspection slots were busy, the report said:

```
  where the input went  (approximate — split by byte share)
  response scan unavailable or partial for 2 request(s): 2 not streamed in a shape shim can read
  spend     ~$0.20  (approximate, 2026-08-30 prices)
```

It now says:

```
  where the input went  (approximate — split by byte share; 2 of 4 requests measured)
  response scan unavailable or partial for 2 request(s): 2 arrived while both inspection slots were busy (parallel agents do this)
  spend     ~$0.20  (approximate, 2026-08-30 prices; API-key equivalent, this session is on a subscription, not a bill)
```

The proxy tells the two routes apart by the *names* of the headers it already
forwards — `x-api-key` is an API key, `authorization` without it is a
subscription — and stores neither value. An API-key session's `spend` line is
unchanged; a mixed one says `3 of 4 requests on a subscription`. The dollar
figure stays on a subscription: it is what the same traffic would cost on an
API key. `shim watch --json` carries `spend_basis` at the top and `auth_route`
and `response_scan_reason` on each exchange.
